# NIST SP 800-154 (Data-Centric System Threat Modeling)

**Focus:** a data-centric methodology — the unit of analysis is a specific
piece of sensitive data and everywhere it flows, rests, or is used, not the
system's components. **Best for:** compliance and data-protection-anchored
assessments where the question is "how could *this specific dataset* be
attacked across its lifecycle," not "what could go wrong with this
architecture" in general.

## The four steps (per NIST SP 800-154 draft)

1. **Identify and characterize the system and data of interest** —
   name the specific sensitive data type(s) in scope (not "all data" — pick
   the actual regulated/sensitive dataset the assessment is about), then
   trace every place it exists: at rest (databases, files, backups, caches,
   logs), in transit (network calls, message queues, exports), and in use
   (in-memory during processing, displayed in a UI, passed to a third
   party/subprocessor). Read the actual code/config/schema to build this —
   don't assume a data flow that isn't verified in the implementation.

2. **Identify and select the attack vectors to include** — for each
   location from step 1, enumerate plausible attack vectors against that
   specific state:
   - *Data at rest*: unauthorized read (misconfigured storage permissions,
     unencrypted backups, a database credential leak), unauthorized
     modification.
   - *Data in transit*: interception (unencrypted or weakly-encrypted
     channels), tampering, a misconfigured trust chain (missing certificate
     validation).
   - *Data in use*: exposure via logging/error messages, over-broad
     in-memory access from a co-located process, exposure to a third party
     beyond its stated processing purpose.
   Not every attack vector applies everywhere the data exists — select the
   ones plausible for each specific location rather than repeating a fixed
   list uncritically.

3. **Characterize the security controls for mitigating the identified
   attack vectors** — for each selected attack vector, name the control that
   addresses it (encryption at rest/in transit, access control, DLP,
   tokenization/masking, audit logging, contractual/processing-purpose
   limits for third parties) and whether it's actually implemented, verified
   from the real code/config — not assumed present because it "should" be.

4. **Analyze the threat model** — review the completed vector/control
   mapping for gaps: any location from step 1 with an identified attack
   vector and no corresponding control is an open finding. This step is
   explicitly iterative in the source methodology — note what would need to
   change (new data location, new third-party integration) to require
   re-running this analysis.
