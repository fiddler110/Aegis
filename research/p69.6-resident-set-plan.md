# P69.6 — Plan a resident set, not one model at a time

Implementation plan. Status: **all seven steps applied 2026-08-17 — SHIPPED.** See §12 for what
landed and where it departs from the design below, and
[releases.md](releases.md#nothing-planned-a-resident-set-2026-08-17-p696) for the record.

Settles the two decisions [roadmap.md](roadmap.md) left open:

- **Budget source:** an explicit `provider.vram_budget_gb` config key. No detection.
- **Plan ownership:** the debate builds a plan and installs it as a scoped override on the
  daemon's context-window cache for its duration. No new workload abstraction.

---

## 0. The shape, in one paragraph

`ollamainfo.RecommendContextWindow(modelMax) int` is one model in, one number out, and that
signature is the bug. Replace it *for the multi-model case only* with a set planner:
`PlanResidentSet(models, budget, kvType) → map[model]window, or a stated refusal`. Solo operation
is the n=1 case and keeps today's answer. A debate resolves its three seats up front, plans the
distinct models among them, installs the resulting windows into the daemon's per-model window cache
under a claim, and restores them on exit. Everything is inert until `provider.vram_budget_gb` is set.

---

## 1. Two facts that constrain the design

**Ollama holds one runner per model name, keyed on its load options.** Changing `num_ctx` for a
resident model forces unload + reload. So the co-resident window and the solo window for the same
model can never coexist — the split is temporal. Any consumer that resolves a window for that model
while a debate is running must get the *planned* number, or it flips the runner back and the debate's
next seat flips it again. `provider.max_concurrent_requests` defaults to 1 for local backends
(`internal/config/config.go:851`), which serializes those requests but does not stop the thrash.

**Consequence: the override has to be daemon-wide for its duration, not per-request.** That is why
it belongs in the context-window cache and not on `provider.Request`.

**Seats that share a model share a runner.** In the measured Topology 1 the proposer and critic are
both `aegis-qwen35-9b` — one runner, one KV cache, one entry in the plan. The planner's unit is a
**distinct model**, not a seat. Deduping by model name before planning is not an optimization; a
planner that budgets three seats when two share weights refuses configurations that fit.

## 2. `internal/ollamainfo` — the set planner

New file `internal/ollamainfo/residentset.go`. Pure arithmetic on top of P69.5's
`KVGeometry`/`BytesPerToken`/`Fit`.

```go
// Member is one distinct model that must be resident at the same time as the others.
type Member struct {
    Model        string
    Geometry     KVGeometry
    WeightsBytes int64
}

// Plan is the per-model window assignment for a resident set.
type Plan struct {
    Windows   map[string]int // model -> serving context window
    KVBytes   map[string]int64
    Weights   int64          // sum
    Total     int64          // weights + KV at the assigned windows
    Budget    int64
    KVType    KVCacheType
}

// PlanResidentSet solves for the largest per-model windows that fit budgetBytes
// with every member resident simultaneously. ok is false when no assignment
// exists; reason states why, for surfacing to the operator.
func PlanResidentSet(members []Member, budgetBytes int64, t KVCacheType) (Plan, bool, string)
```

### 2.1 Allocation policy: equal token windows, not equal bytes

Solve for the largest **token count `T`** such that

```
sum over members of  min(T, ContextMax_i) × BytesPerToken_i  ≤  budget − sum(WeightsBytes_i)
```

by binary search on `T`, then round each assigned window down to `fitStep` (512).

Equal *tokens*, not equal *bytes*, because the window is the number the engine budgets its
conversation against (`tokenest.CompactionTrigger`). Two seats reading the same debate transcript
need comparable room to hold it. An equal-byte split hands the cheap-KV model a window it can never
fill and starves the expensive one on the identical prompt.

The `min(T, ContextMax_i)` clamp gives redistribution for free: a member that hits its training
maximum stops consuming budget as `T` rises, and the search keeps climbing for the others.

Refuse (`ok=false`) when the best `T` lands below `MinFittedContextWindow` (2048), or when weights
alone exceed the budget. `reason` names which — the operator's fix differs.

### 2.2 The floor is not lowered, it is not routed through

`BaselineContextWindow = 32768` stays exactly where it is. The n=1 path still calls
`RecommendContextWindow` and still gets the floor. The multi-member path never calls it — it calls
`Fit`/`PlanResidentSet`, which floor at `MinFittedContextWindow` instead. That satisfies the
roadmap's "do not fix this by lowering `BaselineContextWindow`" literally: the floor keeps doing its
P35.3 job for the single-model case it was written for, and has no say over a co-resident one.

For n=1 **with a budget configured**, take `min(RecommendContextWindow(max), fitted)`. That is the
part of the current behavior that is also wrong on 16 GB — 131072 does not fit the card — and it is
a one-line consequence of the same planner rather than a second code path.

### 2.3 Gathering, split from solving

```go
// PlanFor gathers geometry (/api/show) and resident weights (/api/ps) for each
// model, then plans. Members whose weights cannot be measured yield no plan
// rather than a guessed one.
func PlanFor(ctx context.Context, nativeBase string, models []string, budgetBytes int64, t KVCacheType) (Plan, bool, string)
```

Mirrors the existing `Geometry` / `geometryFromModelInfo` split so the solver is unit-testable
against recorded `model_info` with no live server, which is how `internal/ollamainfo/testdata`
already works.

**Unmeasurable weights is a refusal, not a fallback.** `WeightsBytes` needs a *loaded* model
(`kvfit.go:343`); `/api/tags`' on-disk size overstates qwen35-9b by 2.57 GiB of never-resident
vision projector. A plan built on that number silently eats its own margin.

## 3. `internal/config` — the budget key

`Provider.VRAMBudgetGB float64 \`koanf:"vram_budget_gb"\`` in `internal/config/config.go`, next to
`ContextWindow`.

Semantics to document: **bytes you are willing to let the model server hold**, across every
concurrently resident model — not what the card reports. The topology plan measures ~14.5 GiB usable
on a 16 GB RX 7900 GRE after the WDDM reserve and the desktop compositor; that gap is the operator's
to state, and stating it is the honest alternative to detecting it (P17.5).

`0`/unset = **no planning at all**. Every existing path keeps today's behavior, every existing test
stays green, and the feature only exists for an operator who opted in. This is what makes the whole
change safe to land.

Optional, same step: `Provider.KVCacheType string \`koanf:"kv_cache_type"\`` (`f16`/`q8_0`/`q4_0`,
default `f16`). The planner's arithmetic is ~2× off on a host running `OLLAMA_KV_CACHE_TYPE=q8_0`,
and `models --fit` already has a `--kv-type` flag with no config home
(`internal/cli/modelsfit.go:54`). Aegis cannot read the server's setting, so this is a declaration
the operator must keep in sync; `Footprint.FullyOnGPU` catches a wrong one empirically. Separable
from the rest if it looks like scope.

Validation in `config.Validate`: reject a negative budget; warn when a budget is set on a
non-Ollama provider (it plans nothing there).

## 4. `internal/server` — the scoped override

### 4.1 Install by writing real entries, not by adding a lookup layer

The obvious implementation — a `ctxWinPlanned map[string]int` consulted ahead of the cache in
`effectiveContextWindowFor` — is wrong, and the reason is worth pinning in a comment.

`setWindowLocked` (`internal/server/contextwindow.go:89`) retunes the daemon-wide summarizer when
the model being written is `s.compModel`. A parallel lookup layer bypasses it, so the compactor
would keep compacting against the 51k solo window while the runner serves 16k — the P66.14 class of
disagreement, one layer down.

**So: the claim saves the affected models' `ctxWinEntry` values, writes the planned ones through
`setWindowLocked`, and restores the saved ones on release.** One source of truth, and the summarizer
retune happens correctly in both directions for free.

```go
// claimResidentSet plans windows for models and installs them daemon-wide until
// release is called. A nil budget (provider.vram_budget_gb unset) returns a
// no-op release and no error — planning is opt-in.
func (s *Server) claimResidentSet(ctx context.Context, models []string) (release func(), err error)
```

- Deduplicates `models`, drops empties.
- Serializes on a **1-deep channel semaphore**, not a mutex, so a second concurrent debate waits on
  `ctx.Done()` rather than blocking uninterruptibly for the length of the first. Two concurrent
  debates on one GPU would thrash; queueing them is the correct behavior, and the wait is logged.
- Entries are written with `final: false` so `maybeRefreshContextWindowFor` re-measures reality
  after the first seat loads — the plan is a prediction, `/api/ps` is the verdict.
- Release restores the saved entries, also `final: false`, so the solo window re-detects too.
- On refusal, returns an error naming the members, their weights, the budget, and the shortfall.

New field `s.residentSetSem chan struct{}` (cap 1), initialized in `New`.

### 4.2 `effectiveContextWindowFor` needs no change

Because the plan is written into the cache, `effectiveContextWindowFor` (`contextwindow.go:264`)
already returns it. So does `newEngine` (`engine_build.go:213`), so does `modelAdapter`'s
`WithNumCtx` stamp, and so does any session turn that happens to fire mid-debate — which is exactly
the anti-thrash property. Worth a named test rather than left implicit.

The one visible change is the `src` string: entries installed by a claim get
`src: "plan:resident-set"` so `/status` and the logs say why the window moved.

### 4.3 Refusal timing

The roadmap asks for a refusal "at daemon start rather than mid-debate". The resident set is a
property of the workload, so it is not knowable at daemon start. Two checks, both earlier than
mid-debate:

1. **At debate start** — the earliest point the set is known. Refuse with a stated reason before any
   model turn is spent. This is the one that matters.
2. **At daemon start**, when a budget is configured: check the *global* model alone against it and
   warn (not refuse) if it does not fit. Cheap, catches a mistyped budget before the first turn.

## 5. Wiring the three debate entry points

`debate.withDefaults` (`internal/debate/debate.go:150`) already resolves the persona trio before any
seat runs, so the set is known up front at every entry point. Export it as `debate.WithDefaults`,
plus:

```go
// Seats returns the resolved seats of a debate, for a caller that must plan
// resources before the first role runs.
func Seats(cfg Config) []Seat
```

### 5.1 Daemon — `internal/server/debate.go`

In `handleDebate`, after building `cfg`:

```go
cfg = debate.WithDefaults(cfg)
models := seatModels(cfg)   // enginecfg.DebateSeatModel per seat, deduped
release, err := s.claimResidentSet(r.Context(), models)
if err != nil { writeError(w, http.StatusServiceUnavailable, err.Error()); return }
defer release()
```

`debateRoleRunner` needs no change — its `effectiveContextWindowFor` call
(`internal/server/debate.go:123`) picks up the planned entry.

### 5.2 Agent tool — `internal/tool/builtin/agent.go`

`executeDebate` spawns each role through swarm, which routes back through the daemon's engine path,
so it inherits the plan **provided something claims it**. Add a claim hook alongside the existing
`WithDebateSeatModel` (`agent.go:129`):

```go
func WithResidentSetClaim(claim func(ctx context.Context, models []string) (func(), error)) Option
```

Wired from `enginecfg`/`engine_build.go` to `s.claimResidentSet`; nil = no-op, so non-daemon
embedders are unaffected.

### 5.3 CLI — `internal/cli/debate.go`

Headless, no daemon, no cache. It builds one adapter and passes it to every seat unwrapped
(`internal/cli/debate.go:125`), with a comment conceding the window is whatever the Modelfile pins.
Here the plan rides `provider.WithNumCtx(adapter, plan.Windows[model])` per seat — the same primitive
`modelAdapter` uses. Same planner, same config key, so the CLI and the daemon cannot disagree about
which windows a debate gets, for the same reason `enginecfg.DebateSeatModel` exists.

## 6. `aegis models --fit` — make the planner observable first

Extend `internal/cli/modelsfit.go`:

- `--budget-gb` defaults to `provider.vram_budget_gb` when unset.
- `--fit-set a,b,c` — plan an explicit set, print per-model window / KV / total and the refusal
  reason when there is none.
- `--fit-debate` — resolve the actual seat trio via `enginecfg.DebateSeatModel` and plan *that*.
  This is the closure condition's diagnostic: it answers "will my configured debate fit" without
  spending a debate.

Behavior-neutral, and it lands before anything in §4–5 changes runtime behavior.

## 7. `--first-init` — the closure condition

`internal/tui/wizard.go:506` writes `RecommendContextWindow(modelMax)` unconditionally for the
ollama adapter, which is the row the roadmap measures as not fitting the card at all.

Add one wizard step for the ollama adapter: *"How much VRAM should Aegis assume Ollama can use?
(blank to skip sizing)"*. When answered:

- write `vram_budget_gb`,
- size `context_window` from `Fit` rather than `RecommendContextWindow`,
- when the model is not yet loaded, weights are unmeasurable — write the budget, keep today's
  `RecommendContextWindow` value, and tell the user to run `aegis models --fit --write` after the
  first turn.

When skipped, behavior is byte-identical to today. This is the most user-visible step and the most
bikeshed-prone; it is deliberately last and separable.

## 8. Tests

**`internal/ollamainfo`** (pure, no server):
- Equal-token split over two members with different per-token costs.
- `ContextMax` clamp on one member redistributes to the other.
- Duplicate model names collapse to one member — the proposer/critic case. A planner that
  double-counts here refuses a set that fits, so this is a correctness test, not a tidiness one.
- Refusal below `MinFittedContextWindow`; refusal when weights alone exceed budget; distinct reasons.
- n=1 agrees with `Fit` exactly.
- Regression pinning the measured Topology 1 pair against a 14.5 GiB budget, asserting the assigned
  windows are at least the hand-fitted 16000 the topology plan measured as working.

**`internal/server`**:
- `TestResidentSetClaimInstallsAndRestores` — entries before, during, after; `final` false on both
  transitions.
- `TestSessionTurnDuringADebateSeesThePlannedWindow` — the anti-thrash property, named so the reason
  survives.
- `TestResidentSetClaimRetunesAndRestoresTheSummarizer` when `compModel` is in the set.
- `TestConcurrentResidentSetClaimsSerialize`, and that a queued claim honors `ctx` cancellation.
- Unset budget ⇒ no-op release, no entry touched.

**`internal/config`**: key parses; `0` is inert; negative rejected.

**Unchanged and asserted so**: `TestRecommendContextWindow` and `BaselineContextWindow` — a test
that the floor is still 32768 and still applies on the n=1 path.

## 10. Two corrections to the source documents, to make while here

**[roadmap.md](roadmap.md), P69.6:** "32768 alone is 8.12 GiB, leaving no room for the 5.08 GiB
arbiter". At the geometry both documents record — 33 blocks × 4 KV heads × (256+256) = 135,168
bytes/token at f16 — 32768 tokens is **4.13 GiB of KV**; 8.12 GiB is weights + KV, i.e. the model's
whole footprint. Read that way the sum is 8.13 + 5.08 = **13.21 GiB against a 14.5 GiB budget, which
fits** — with ~1.3 GiB spare. The floor is therefore *marginal* for this pair rather than impossible,
and the claim that it "cannot express a co-resident configuration on 16 GB at all" is too strong. It
does bind for three seats, for a 14B arbiter, or once the KV cache is actually filled to the window
rather than measured at low occupancy.

This does not weaken the item — the planner is still what is missing, and a 1.3 GiB margin is not
something to ship by accident — but it changes what step 8's regression test should assert, so it
should be corrected before the test is written to a wrong premise.

**[debate-topology-plan.md](debate-topology-plan.md) §1.2:** the Topology 1 table labels its KV
column `q8_0`, but its measured resident figures match f16 — 4.00 GiB weights + 2.06 GiB f16 KV =
6.06 GiB against 6.02 measured, where q8_0 would predict 5.10. Those measurements were taken at f16,
so q8_0 remains **unspent headroom**, not headroom already counted. Relabel the column.

Both are worth re-measuring with `research/scripts/vram_topology_probe.py` before step 8 pins a
number.

## 11. Open question left for implementation

Whether a **session turn that arrives mid-debate should be served the planned (smaller) window, or
queued behind the claim.** §4.2 does the former, which is thrash-free and simple, but it means an
interactive turn silently gets a smaller window for the debate's duration — visible only as earlier
compaction. Queueing is more honest and worse to use. Serving the planned window is the right default;
the alternative belongs behind a config key if it is ever wanted, not in the first version.

Settled as designed in step 4, and pinned by
`TestSessionTurnDuringADebateSeesThePlannedWindow` so the reason survives.

## 12. What landed, and where it departs from the design

**New files:** `internal/ollamainfo/residentset.go` (+ tests),
`internal/server/residentset.go` (+ tests), `internal/config/vrambudget_test.go`.
**Touched:** `internal/config/config.go`, `internal/cli/modelsfit.go`, `internal/cli/models.go`,
`internal/debate/debate.go`, `internal/server/contextwindow.go`, `internal/server/server.go`.

Thirteen departures, each with a reason:

1. **A claim never *raises* a window.** Not in §4 and it should have been. `installPlan` skips any
   model whose current window is already at or below the planned one. Without it, the common case —
   every debate seat on the same model — plans a window *larger* than the detected one, so each
   debate would pay a cold unload/reload to gain context nobody asked for. Shrinking is the only
   direction a claim buys anything in. `TestResidentSetClaimNeverRaisesAWindow` pins it.

2. **There is no `config.Validate` to put validation in.** §3 assumed one; `internal/config` has no
   validation entry point at all. So validation is split where it can actually live:
   `VRAMBudgetBytes()` reads a negative budget as zero (a budget is an opt-in hardware hint — failing
   the daemon over a typo is the worse trade), `KVCacheTypeValid()` reports an unrecognized cache
   type, and `Server.warnResidentBudget` does the daemon-start warning §4.3 asked for, including the
   "budget set on a non-Ollama provider" case.

3. **The daemon-start check stays silent when nothing is measured.** At daemon start the model is
   normally not loaded, so weights are unmeasurable and the planner refuses for that reason. Warning
   on it would train the operator to ignore the warning that matters, so `isUnmeasuredReason` filters
   those out and only a genuine "does not fit" is warned about.

4. **The semaphore is created lazily (`residentSetGate`), not in `New`.** `Server` values are built
   field-by-field throughout `internal/server`'s tests, and a nil channel is not an empty semaphore —
   it is a deadlock.

5. **`debate.WithDefaults` and `debate.Seats` were exported in step 3, not step 5.** `--fit-debate`
   needs the resolved seat trio, and re-deriving it in the CLI would let the diagnostic pass while
   the debate it diagnoses runs on different models.

6. **`--kv-type`'s flag default changed from `"f16"` to `""`.** A flag default of `f16` would shadow
   `provider.kv_cache_type` permanently; empty means "unset", and the config supplies it. Empty is
   already f16 to `ollamainfo`, so no behavior moved.

7. **`Plan` grew three reporting members** — `MemberWeights`, `Collapsed`, `Spare()` — plus
   `ollamainfo.BudgetBytes`. `Collapsed` is the one that matters: a report showing two rows for three
   seats looks like it lost a model unless it can say the third shares a runner.

8. **The regression test asserts against the hand-fitted 16000 and the stated 14.5 GiB budget**, not
   against the topology plan's measured column — see §10's second correction, now recorded in
   `debate-topology-plan.md` itself. Both of those inputs are stated rather than inferred, so the test
   does not inherit the discrepancy.

9. **A claim cannot preserve the global model's `max`.** `windowLocked` synthesizes the global
   model's entry from the `ctxWin`/`ctxWinSrc`/`ctxWinFinal` fields, which predate `ctxWinEntry.max`,
   so the global model has never carried a training maximum. Pre-existing (P52.1), out of scope here,
   and noted in the test so it is not mistaken for a claim bug. Non-global models carry it through
   correctly.

### Steps 5–7, and four more departures

10. **Four entry points, not three.** §5 counted the daemon, the agent tool and the CLI. The TUI's
    `/debate` is a fourth — it goes through `POST /debate`, so it inherits the claim, but it is worth
    naming because "three" would leave a reader looking for a fourth wiring site that does not exist.

11. **A claim of all-blank models is a no-op, not a refusal.** The agent tool offers
    `a.debateSeatModel(seat.Persona)` for each seat, which is `""` when no resolver is wired. Passing
    three blanks to the planner would have produced "no models to plan for" — reported as a set that
    could not be fitted, refusing debates that are perfectly fine. `claimResidentSet` now returns a
    no-op when nothing is named.

12. **The wizard's note travels in the message, not on the model.** `saveCmd` runs in a `tea.Cmd`
    goroutine, so writing `w.fitNote` there would race the renderer. It rides `wizardSavedMsg`
    instead, and is appended to the transcript rather than shown in the wizard's own view — the
    wizard closes the instant it saves, so its view is the wrong place for something the user has to
    act on.

13. **`ProviderPatch` gained `VRAMBudgetGB`.** `PatchGlobalProvider` rebuilds the whole provider
    block, so a key it does not know about is a key first-init cannot write. It is emitted with its
    rationale as a comment, next to `context_window`, for the same reason
    `PatchGlobalContextWindow` is surgical: a calibrated number looks arbitrary without one.

Full suite green with all seven steps applied, and the feature is inert until
`provider.vram_budget_gb` is set.
